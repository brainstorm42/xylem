# Percolation source capture and Xylem index

This is a public, reproducible integration of the pinned upstream
`formal-math` percolation project at revision
`795efb86f191735c5481675763537cfb4ff37e55`.

The bundled `upstream/` directory is the content-addressed source snapshot
(265 files, 251 Lean files). The import graph scans the 250 theorem-corpus Lean
files; `scripts/Axioms.lean` is retained in the snapshot and audited
separately. `data/source-manifest.json`, `data/import-graph-manifest.json`, and
`data/reproducibility-receipt.json` record hashes and coverage. The release
assembly and LFS boundary are recorded in the [integration provenance](../../../provenance/PERCOLATION-INTEGRATION.md).

## Two Lean surfaces

`Solution.lean` and `Challenge.lean` cannot be imported together: both define
the same `BondPercolation.*` names. They are therefore elaborated separately:

* `Extract.lean`: imports `Percolation`, `Solution`; 11,773 declarations.
* `ExtractChallenge.lean`: imports `Percolation`, `Challenge`; 11,772 declarations.

The merged capture qualifies local IDs as `solution::...` and `challenge::...`.
It does not claim that the two public theorem surfaces are equivalent. The
Challenge build emits two `sorry` warnings (`Challenge.lean:143` and `149`),
while the selected Solution endpoint has no `sorryAx` in the fresh audit.

## Proof decomposition and capture audit

`data/components.json` is the authored role-label input. The indexed component
file is `data/components-generated.json`: it preserves those labels with literal
signature/binder audits, adds 228 compiler-derived source-module regions, and
adds a complete traversal-derived trace-backed interface layer. The source-module
regions are generated by walking the captured `USES_IN_PROOF` cone from
`solution::BondPercolation.percolation_continuity` and partitioning reachable
declarations by their exact Lean source module. They are source partitions, not
mathematical subargument boundaries. The generated layer contains 8,134
reachable Solution declarations and 1,702 cross-region proof boundaries; it is
not a manually selected reading map.

The structural application layer is generated from the complete deterministic
reachable local proof-cone traversal in `data/proof-trace.json.gz`, without a
second hand-written target list. The trace contains 8,063 proof-cone declaration
records, 3,314,889 exact retained application records, and 28,919,499 retained
local reference records. Of the applications, 106,395 are proof-valued and
3,208,494 are data-valued or proposition-valued. It classifies application
results using their instantiated result type: proof-valued applications are
proof evidence, while data-valued and Prop-valued predicate applications remain
data evidence. The
trace accounts for 299,496,929 omitted external/structural applications and
622,384,457 omitted external references rather than silently dropping them.
The component layer stores deterministic bounded samples plus exact counts;
the full trace remains the evidence source. Type-only statement references are
recorded separately and are not promoted to proof applications. The generated
layer currently exposes 8,063 trace-backed source nodes; because the complete
cone includes every discovered local target, target boundaries are represented
by those source nodes rather than duplicated as separate target nodes. All
counts are recorded in the component and validation audits.

Of the 8,063 traversal records, 7,883 have retained elaborated values and 180
are explicit valueless constants: 97 constructors, 74 inductives, and 9
recursors. The audit rejects `no_value` for theorem, definition, opaque, or
axiom records.

The independent validator reports PASS with 5,340 local proof-assumption
applications, 197,963 `w/e` data applications, and 16,831 `g/e` data
applications; neither data head was promoted to proof evidence. Its mutation
test rejects swapped arguments, and its type-only test keeps the AdditiveGluing
and NearOneGluing statement constants out of proof-application evidence.
`reconstruction/SubargumentSpine.lean` checks the reusable CSH interface, a
direct local-assumption application, the named CSH-to-Conjecture-3-to-near-one
chain, the theorem-6 input, and the reassembled public endpoint. It does not
inline opaque theorem bodies; the local helper bodies remain named captured
declarations. The audit and independent validator distinguish compiler edges,
trace records, assumptions, and type-only references; the short mathematical
descriptions remain pending human review.

`data/proof-trace.json.gz` is the compact full-cone artifact: it retains exact
local proof/data applications and local references, records per-declaration
omission counts, and omits repeated structural trees by policy. The separate
`data/proof-trace-boundaries.json.gz` retains full elaborated `Expr` trees for
the reviewed boundary declarations (including `cshHolds`) with no fuel
truncation. Both are structural evidence rather than a claim that opaque
theorem constants have been inlined. `data/capture-audit.json` accounts for all
32 empty local premise
lists and all 390 null signature trees. The empty lists are 30 inductive heads
plus the lambda-only `coordShift` definition; the null trees are diagnosed as
over-application ambiguity, `let`, or projection nodes. Proof-use extraction is
independent of this signature renderer.

## Restore and query

The full-fidelity declaration capture is `data/declarations.json.gz`; the
queryable SQLite index is `data/xylem.db.gz` (the uncompressed database is
generated and ignored because it is large). Restore it before querying:

```sh
python3 restore_index.py --config xylem-e2e-config.json
python3 ../../canonical/run.py --config xylem-e2e-config.json query status --json
python3 ../../canonical/run.py --config xylem-e2e-config.json query overview --surface solution --json
python3 ../../canonical/run.py --config xylem-e2e-config.json query components component:all-dimensions-endpoint --json
python3 ../../canonical/run.py --config xylem-e2e-config.json query components \
  component:trace-subarg-BondPercolation-percolation_continuity-ace27358 --json
python3 ../../canonical/run.py --config xylem-e2e-config.json query path \
  solution::BondPercolation.percolation_continuity \
  solution::Percolation.Literature.KozmaNitzan2024_thm6_holds --json
python3 ../../canonical/run.py --config xylem-e2e-config.json mcp
```

Use the isolated Python environment described by
`canonical/requirements.txt` for the MCP command. The checked component input
is `data/components-generated.json`. Its generated memberships, exact
interfaces, and compiler relations are validated against the captured IDs and
`USES_IN_TYPE`/`USES_IN_PROOF` rows at build time. Its role prose remains
`authored_pending_review`; it is not a claim that Lean establishes explanation
quality or literature correspondence.

The formal endpoint is exactly `theta (zdGraph d) 0 (criticalProbI d) = 0`.
Upstream prose calls this equivalent to continuity of `p ↦ theta p` using
separate off-critical continuity theorems, but this index does not silently turn
that contextual statement into a stronger formal theorem or certify the
literature correspondence.

The committed capture and index are the first-use route. Restore the compressed
SQLite database after hydrating Git LFS; the restore script checks the committed
archive before writing the ignored working database. The small CLI/MCP runtime
still needs the declared Python packages from `canonical/requirements.txt`.

The release regression check keeps two states separate: it verifies the raw
archive byte hash before rebinding freshness, then verifies the relocated
working database with SQLite integrity, graph counts and identities, source
locations, and the intended package-relative input snapshot. It does not
require the private producer Git commit recorded in the historical receipt;
that receipt is anchored by the shipped release manifest. A corrupted archive
is covered by a negative test and must fail the raw identity check.

## Rebuild from source

The upstream commands run with the repository's `leanprover/lean4:v4.32.0`
toolchain and exact `lake-manifest.json`. A fresh build is not offline: `lake
exe cache get` downloads the pinned Mathlib cache, and Lake builds missing
dependencies from the pinned project files. The committed receipts record the
checked build, extraction, replay, and audit results; rebuilding is an optional
verification route.

```sh
# Run from the repository root.
cd xylem-plugin/examples/percolation-e2e
cd upstream
lake exe cache get
lake build
lake build Challenge
lake env lean scripts/Axioms.lean
cd ../../..
python3 capture/percolation/build_import_graph.py ...
python3 capture/percolation/prepare_capture.py ...
WORK="$(mktemp -d)"
python3 capture/percolation/run_batched_trace.py \
  --upstream examples/percolation-e2e/upstream \
  --extractor capture/percolation/ExtractProofTrace.lean \
  --manifest "$WORK/percolation-proof-cone-manifest.json" \
  --output examples/percolation-e2e/data/proof-trace.json.gz \
  --batch-size 50
python3 canonical/run.py --config examples/percolation-e2e/xylem-e2e-config.json build
```

To rerun the committed audit/decomposition layer, run these commands from this
example directory:

```sh
WORK="$(mktemp -d)"
python3 ../../capture/percolation/audit_capture.py \
  --capture data/declarations.json.gz \
  --source-revision 795efb86f191735c5481675763537cfb4ff37e55 \
  --output "$WORK/capture-audit.json"
python3 ../../capture/percolation/derive_proof_components.py \
  --capture data/declarations.json.gz \
  --roles data/components.json \
  --proof-trace data/proof-trace.json.gz \
  --source-revision 795efb86f191735c5481675763537cfb4ff37e55 \
  --output "$WORK/components-generated.json" \
  --audit-output "$WORK/component-audit.json"
python3 ../../capture/percolation/validate_subarguments.py \
  --components "$WORK/components-generated.json" \
  --proof-trace data/proof-trace.json.gz \
  --client reconstruction/SubargumentSpine.lean \
  --output "$WORK/subargument-validation.json"
cmp "$WORK/capture-audit.json" data/capture-audit.json
cmp "$WORK/components-generated.json" data/components-generated.json
cmp "$WORK/component-audit.json" data/component-audit.json
cmp "$WORK/subargument-validation.json" data/subargument-validation.json

# In the pinned upstream environment, check the named interface client:
cd upstream
lake env lean ../reconstruction/SubargumentSpine.lean
cd ..
```

The index build is byte-reproducible. From this example directory, set
`WORK="$(mktemp -d)"`, then after restoring or rebuilding `data/xylem.db` create
the archive with `gzip -n -9 -c data/xylem.db > "$WORK/xylem.db.gz"` and compare
it with `data/xylem.db.gz`; the E2E test also checks the committed archive restore
and SQLite hash.

The extractor retains statement/type text, source ranges, axioms, and separate
type/proof premise flags. The full capture retains diagnosed signature-tree
fallbacks, while the compact proof-cone trace retains exact local elaborated
application/reference evidence and the boundary artifact retains selected
full `Expr` trees. Opaque theorem constants are not inlined; proof-use rows
come from Lean's `allowOpaque` elaborated constant values. The compact SQLite
projection omits repeated premise arrays and expression trees from node props,
but retains every edge and points back to the compressed full capture.

Run the regression/E2E check with:

```sh
python3 ../../tests/test_percolation_e2e.py
```

## Limitations

The two Lean surfaces elaborate separately because `Solution.lean` and
`Challenge.lean` define colliding names. The Challenge surface intentionally
retains two `sorry` placeholders; the selected Solution endpoint has no
`sorryAx` in the recorded audit. The index does not claim equivalence between
the two surfaces.

Compiler-derived source-module regions partition reachable declarations by
source file; they do not constitute mathematical subargument boundaries.
Trace-backed relations record structural proof/data applications and omission
counts, while opaque theorem constants remain named rather than inlined.
Authored component descriptions remain pending human review, and the exact
endpoint `theta (zdGraph d) 0 (criticalProbI d) = 0` is not promoted to a
broader continuity or literature-equivalence claim.

The committed index and large capture artifacts require Git LFS hydration, and
the query/MCP route requires the Python packages listed in
`canonical/requirements.txt`. Rebuilding from the source snapshot is a separate
verification route that downloads the pinned Lean/Mathlib cache and may build
Lake dependencies; this release does not promise an offline rebuild. These
constraints describe the release boundary, not a failure of the captured
artifacts themselves.

The committed capture, compressed trace, boundary artifact, and SQLite index
are evidence for the recorded run. Querying the index requires Git LFS
hydration and the declared Python runtime; source rebuilding downloads the
pinned Lean/Mathlib dependencies as described above. The package does not
promise an offline rebuild.
